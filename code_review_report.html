一、安全问题

严重 API 密钥硬编码在源码中 backend/config.py:3 安全

DeepSeek LLM 的 API Key 以明文形式硬编码在 config.py 中，作为默认值：

LLM_API_KEY = os.environ.get('LLM_API_KEY', 'sk-51151dbb41e047029c02bd2bbfc61387')

该密钥会随代码提交到版本库，任何能访问代码仓库的人都能获取。此外 deploy_nas.md 中暴露了默认账号密码 yewei / 123456。

修复建议：移除硬编码密钥，仅从环境变量读取；将 config.py 加入 .gitignore 或使用 .env 文件；轮换已泄露的密钥。

严重 CORS 配置允许任意来源 + 凭证 backend/app.py:27-31 安全

同时设置 Access-Control-Allow-Origin: * 和 Access-Control-Allow-Credentials: true，这在浏览器规范中实际不生效（浏览器会拒绝），但说明安全意识缺失：

response.headers.add('Access-Control-Allow-Origin', '*') response.headers.add('Access-Control-Allow-Credentials', 'true')

修复建议：在生产环境中应配置为具体的前端域名，如 http://NAS_IP:8088，而非通配符 *。

严重 SQL 注入风险 — Dashboard 拼接 SQL backend/app.py:1222-1235 安全

Dashboard 接口中使用 f-string 直接将 Python 变量拼入 SQL 语句，虽然当前变量来自服务端计算（时间），但这种模式极易在后续迭代中引入注入漏洞：

date_condition = f"WHERE created_at >= '{now.year}-{str(start_month).zfill(2)}-01'" cursor.execute(f"SELECT COUNT(*) as total FROM customers {date_condition}")

同样的问题出现在第 1259、1263、1269、1275、1282 行等多处。

修复建议：统一使用参数化查询 cursor.execute("... WHERE created_at >= ?", (date_str,))。

高 下载接口允许 Token 通过 URL 查询参数传递 backend/app.py:2404-2406 安全

download_contract_file 接口允许从 URL 查询参数获取 token：

if not token: token = request.args.get('token', '')

URL 中的查询参数会被记录在浏览器历史、Nginx 日志、Referer 头中，导致 token 泄露风险。

修复建议：移除查询参数获取 token 的逻辑，统一使用 Authorization 头。如需支持浏览器直接下载，可使用临时签名 URL。

高 文件上传缺乏安全校验 backend/app.py:2358-2394 安全

upload_contract_file 接口仅基于文件扩展名判断，未校验文件内容。攻击者可上传伪装为 PDF 的恶意文件。同时未限制文件大小。

修复建议：使用魔术字节（magic bytes）校验文件实际类型；限制文件大小；对上传文件进行病毒扫描；使用独立的存储域名。

高 搜索接口未做数据权限隔离 backend/app.py:2321-2355 安全

/api/search 接口虽然验证了 token，但搜索结果未按用户角色过滤。普通用户可以通过全局搜索看到其他人的客户、商机、合同数据。

修复建议：对非主任/院长角色，在搜索 SQL 中增加 WHERE owner_id = ? 过滤条件。

高 登录接口缺少速率限制和暴力破解防护 backend/app.py:187-211 安全

登录接口没有任何速率限制、账号锁定机制或验证码，攻击者可无限次尝试密码。

修复建议：增加登录失败计数与账号临时锁定（如 5 次失败后锁定 15 分钟）；引入 flask-limiter 做 API 速率限制。

中 SECRET_KEY 使用弱默认值 backend/app.py:38 安全

SECRET_KEY 有一个可预测的默认值 "crm_secret_key_2026"，虽然当前未使用 Flask session，但如果后续启用会存在风险。

修复建议：强制从环境变量读取，不提供默认值；启动时检查是否已设置。

中 错误信息直接暴露给客户端 backend/app.py:404-406 等多处 安全

多个接口的异常处理直接将 str(e) 返回给前端：

return jsonify({'code': 500, 'message': str(e), 'data': None})

这可能暴露数据库表结构、SQL 语句等内部信息。

修复建议：记录详细错误到日志，返回给客户端通用错误信息如"服务器内部错误"。

二、Bug 与逻辑缺陷

严重 前端 token 存储 key 不一致导致通知功能失效 frontend/src/views/Layout.vue:188 Bug

auth.js 中存储 token 使用的 key 是 crm_token，但 Layout.vue 中读取时使用的是 token：

// auth.js (正确) localStorage.setItem('crm_token', token.value) // Layout.vue (错误) const token = localStorage.getItem('token') // 永远返回 null

这导致 fetchUnreadCounts() 中的所有请求都缺少 Authorization 头，返回 401，通知和预警计数永远为 0。

修复建议：将 Layout.vue 第 188 行改为 localStorage.getItem('crm_token')，或直接使用 authStore.token。

高 GET 请求中执行写操作（INSERT/UPDATE） backend/app.py:921-949 Bug

GET /api/business 接口在查询商机列表的同时，执行了周计划归档的 INSERT 和 UPDATE 操作。这违反了 HTTP 语义——GET 应为幂等的只读操作。

后果：浏览器预取、爬虫、或用户刷新页面都会触发数据归档逻辑，可能导致周计划被多次归档或数据错乱。

修复建议：将周计划归档逻辑拆分为独立的 POST 接口或定时任务（如 APScheduler），GET 接口仅负责查询。

高 删除合同后未清理关联的回款记录 backend/app.py:707-734 Bug

delete_contract 接口直接删除合同记录，但未清理 payment_records 表中关联的回款记录。这会导致数据库中存在大量孤儿回款记录，且 JOIN contracts c ON pr.contract_id = c.id 查询时这些记录的合同信息为 NULL。

修复建议：删除合同前先删除关联的回款记录，或使用软删除标记合同为"已删除"状态。

高 合同编号重复时的 fallback 逻辑引用未定义变量 backend/app.py:379-381 Bug

当 contract_no 为空时进入 if 分支计算 max_id，但当 contract_no 不为空但重复时，进入下面的 if 分支，引用了 max_id 变量——但此时 max_id 可能未定义：

if not contract_no or contract_no.strip() == '': cursor.execute("SELECT MAX(id) FROM contracts") max_id = cursor.fetchone()[0] or 0 # 仅在此分支定义 contract_no = f"HT..." cursor.execute("SELECT COUNT(*) FROM contracts WHERE contract_no = ?", (contract_no,)) if cursor.fetchone()[0] > 0: # 如果上面 if 没进，max_id 未定义，下面会 NameError contract_no = f"HT...{str(max_id + 1).zfill(3)}..."

修复建议：在函数开头初始化 max_id = None，或在重复分支中重新查询 MAX(id)。

中 login 接口未处理 request.json 为 None 的情况 backend/app.py:189-191 Bug

当请求未携带 JSON body 或 Content-Type 不正确时，request.json 会返回 None，此时 data.get('username') 会抛出 AttributeError。

data = request.json # 可能为 None username = data.get('username') # AttributeError: 'NoneType' has no attribute 'get'

修复建议：使用 data = request.get_json(silent=True) or {}。此问题在多个接口中存在。

中 删除客户/商机接口缺少权限校验 backend/app.py:825-848, 1041-1064 Bug

delete_customer 和 delete_business 接口仅验证了 token 有效性，但未检查当前用户是否有权删除该数据。普通用户可以删除其他人的客户和商机。

修复建议：在删除前检查 owner_id 是否匹配当前用户，或限制仅主任/院长可删除。

低 requirements.txt 缺少 openpyxl 依赖 backend/requirements.txt Bug

app.py 中使用了 openpyxl（合同/回款导入解析）和可选的 xlrd（.xls 文件支持），但 requirements.txt 中仅列出了 Flask、bcrypt、Werkzeug、requests。导入功能在全新部署时会报 ModuleNotFoundError。

修复建议：添加 openpyxl>=3.1.0 和 xlrd>=2.0.1 到 requirements.txt。

三、架构与设计问题

高 单文件 3100+ 行，职责严重耦合 backend/app.py 架构

整个后端逻辑集中在单个 app.py 文件中（3135 行），包含路由定义、数据库操作、业务逻辑、LLM 调用、QA 引擎等。这导致：

  • 难以维护和协作开发
  • 无法进行单元测试
  • 代码复用困难（如 token 验证逻辑在每个路由中重复）

修复建议：按功能拆分为蓝图（Blueprint）：auth_bp、contract_bp、customer_bp、business_bp、payment_bp、qa_bp 等。将数据库操作提取为独立的 model 层。

高 Token 验证逻辑在每个路由中重复 backend/app.py 全文 架构

几乎每个路由函数的前 4 行都是相同的 token 验证代码：

token = request.headers.get('Authorization', '').replace('Bearer ', '') payload = verify_token(token) if not payload: return jsonify({'code': 401, 'message': '登录已过期', 'data': None})

这段代码在 40+ 个路由中重复出现。

修复建议：使用 Flask 装饰器 @login_required 统一处理认证，减少代码重复，也便于后续扩展权限控制。

高 SQLite 用于生产环境且 check_same_thread=False backend/app.py:125 架构

SQLite 是单文件数据库，不支持并发写入。当前设置 check_same_thread=False 允许多线程访问，但没有加锁，在并发写入时可能导致 database is locked 错误。

此外，Dockerfile 中 COPY crm_app.db . 将数据库文件打包进镜像，虽然 docker-compose 通过 volume 覆盖了它，但镜像中仍包含一份初始数据库副本。

修复建议：对于多用户生产环境，建议迁移到 PostgreSQL 或 MySQL。如必须使用 SQLite，应启用 WAL 模式 (PRAGMA journal_mode=WAL) 并添加写入锁。

中 数据库 Schema 通过 try-except ALTER 动态迁移 backend/app.py:42-108 架构

init_business_table() 和 init_operation_logs_table() 通过 try: ALTER TABLE ... except: pass 的方式做数据库迁移。这种方式：

  • 无法区分"列已存在"和"真实错误"
  • 没有版本管理，无法回滚
  • 每次请求都调用（通过 get_db），浪费性能

修复建议：使用 Flask-Migrate（Alembic）做正式的数据库迁移管理；将迁移逻辑移到应用启动时执行一次，而非每次请求。

中 角色权限通过硬编码中文字符串判断 backend/app.py 全文 架构

权限判断逻辑散布在各路由中，使用硬编码的中文字符串：

if role == '主任' or role == '院长':

这种模式无法统一管理权限策略，且中文字符串容易出错（如空格、全半角）。

修复建议：定义角色常量（如 ROLE_ADMIN = 'admin'），使用装饰器 @role_required('admin') 统一控制；或引入 RBAC 权限模型。

低 前端路由缺少完整的角色权限控制 frontend/src/router/index.js:90-113 架构

路由守卫仅对 /operation-logs 做了角色判断，其他管理页面（如 /users）没有前端路由级别的权限控制，虽然后端 API 有校验，但用户能看到入口。

修复建议：在路由 meta 中声明所需角色，在守卫中统一校验。

四、性能问题

高 每次请求都执行数据库 Schema 检查 backend/app.py:123-129 性能

get_db() 函数在首次连接时调用 init_business_table() 和 init_operation_logs_table()，这两个函数执行多次 ALTER TABLE 和 CREATE TABLE 操作（每次都触发异常再 pass）。虽然 SQLite 对已存在的列 ALTER 会快速失败，但仍然是每次新连接都执行的不必要开销。

修复建议：将初始化逻辑移到应用启动时执行一次（if __name__ == '__main__' 之前），或使用 Flask 的 before_first_request（Flask 2.3+ 已移除，可用 click.command 或手动调用）。

中 Dashboard 接口执行大量独立查询 backend/app.py:1204-1436 性能

单个 /api/dashboard 请求会执行 8-12 个独立的 SQL 查询（统计 + 图表 + 排行），每个查询都同步执行。在数据量增长后，接口响应时间会显著增加。

修复建议：合并相关统计查询；对 Dashboard 数据做缓存（如 5 分钟刷新一次）；考虑使用 Redis 缓存热点统计数据。

中 导入解析接口一次性加载全部合同到内存 backend/app.py:539-540, 630-631 性能

合同和回款的导入解析接口执行 SELECT contract_no FROM contracts 加载全部合同编号到内存做去重。当合同数量增长到数万条时，这会消耗大量内存。

修复建议：改为按需查询（对每行数据用 SELECT 1 FROM contracts WHERE contract_no = ? 检查），或使用批量 WHERE contract_no IN (...) 查询。

低 前端轮询间隔过短 frontend/src/views/Layout.vue:242 性能

Layout 组件每 30 秒轮询一次未读消息和预警计数，每次发起 2 个 HTTP 请求。对于 CRM 系统来说频率偏高。

修复建议：将轮询间隔增加到 60-120 秒，或改用 WebSocket/SSE 推送通知。

五、代码质量与规范

中 裸 except 捕获所有异常 backend/app.py:47-83, 560, 1693 等多处 代码质量

大量使用 except: 或 except Exception as e: 捕获所有异常，包括 KeyboardInterrupt、SystemExit 等：

try: cursor.execute("ALTER TABLE business ADD COLUMN address TEXT") except: pass # 吞掉所有错误，包括真正的数据库错误

修复建议：使用具体的异常类型如 except sqlite3.OperationalError；不要静默吞掉异常，至少记录日志。

中 大量调试脚本残留在项目中 backend/ 目录下多个文件 代码质量

以下文件为临时调试/修复脚本，不应出现在生产代码库中：

文件用途
check_files.py检查合同文件路径
check_follow_logs.py检查跟进日志
query_plan.py查询计划
debug_plan.py调试计划
fix_none_values.py修复空值
check_none.py检查空值
add_note_column.py添加备注列
test_api.pyAPI 测试

修复建议：将这些脚本移到 scripts/ 或 tools/ 目录，或直接删除已无用的。正式的数据迁移应使用 Alembic。

低 debug print 语句散布在代码中 backend/app.py:19, qa_engine.py:8,24,34,42,45,48 等 代码质量

qa_engine.py 中大量 print(f"[LLM Debug] ...") 语句，app.py:2399 也有 print("DEBUG: test_download_route called")。这些调试输出在生产环境会污染日志。

修复建议：使用 Python logging 模块替代 print，配置日志级别。

低 前端使用 emoji 作为图标 frontend/src/views/Layout.vue 全文 代码质量

侧边栏菜单使用 emoji（🚀📊🎯📜💰🌊⏱️📋👥🔔🔍🤖📝）作为图标，在不同操作系统和浏览器中显示效果不一致，且无法控制颜色和大小。

修复建议：使用 Element Plus 内置的 el-icon 组件或 SVG 图标库（如 @element-plus/icons-vue）。

六、部署与配置问题

高 Dockerfile 使用 exec(open().read()) 启动应用 Dockerfile:15 部署

Dockerfile 的 CMD 使用了一种极不常规的启动方式：

CMD ["python", "-c", "import os; os.environ['FLASK_DEBUG'] = '0'; exec(open('app.py').read())"]

这种方式的问题：① 不支持信号传递（Ctrl+C/SIGTERM 无法优雅关闭）；② __name__ 不等于 '__main__'，如果代码中有 if __name__ == '__main__' 的逻辑将不会执行；③ exec(open()) 有安全风险。

修复建议：改为 CMD ["python", "app.py"]，或使用 gunicorn 生产服务器：

CMD ["gunicorn", "-w", "4", "-b", "0.0.0.0:5000", "app:app"]
高 docker-compose 中 LLM_API_KEY 为空 docker-compose.yml:15 部署

docker-compose.yml 中 LLM_API_KEY= 为空值，但 config.py 中有硬编码的默认值。部署到 NAS 后，如果环境变量未设置，会使用硬编码的密钥——但该密钥可能已失效或被泄露。

修复建议：使用 Docker secrets 或 .env 文件管理密钥；移除 config.py 中的默认密钥值。

中 Nginx 缺少安全响应头和性能优化配置 nginx.conf 部署

Nginx 配置过于简单，缺少：

  • X-Content-Type-Options: nosniff
  • X-Frame-Options: DENY
  • X-XSS-Protection: 1; mode=block
  • Gzip 压缩配置
  • 客户端请求体大小限制（client_max_body_size），影响文件上传
  • 静态资源缓存策略
  • HTTPS 配置（当前仅 HTTP）

修复建议：添加安全头和性能优化配置；对上传接口设置合理的 client_max_body_size（如 50M）。

中 Dockerfile 将数据库文件打包进镜像 Dockerfile:9 部署

COPY crm_app.db . 将整个数据库文件打包进 Docker 镜像。虽然 docker-compose 通过 volume 挂载覆盖了它，但：

  • 镜像体积不必要地增大
  • 镜像中包含初始数据（可能含用户密码 hash），存在信息泄露风险
  • 每次数据库变更都需要重新构建镜像

修复建议：从 Dockerfile 中移除 COPY crm_app.db .，改为在启动时检查数据库是否存在，不存在则初始化空数据库。

低 deploy_nas.md 暴露默认凭据 deploy_nas.md:73 部署

部署文档中明文写了默认账号密码 yewei / 123456。

修复建议：从文档中移除默认密码；首次登录强制修改密码；密码应使用 bcrypt 加密存储（当前已使用 bcrypt，这点是好的）。
